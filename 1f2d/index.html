说明：本文以原始 Markdown 与 CommonMark 通用的写法为主。删除线、表格等虽被现代编辑器普遍支持，但严格意义上属于 GFM 扩展。因支持面极广、几乎人人都在用，这里一并讲解，并在标题处明确标注“GFM 扩展”。

一、Markdown 的起源、发展与特点

1.1 它是什么

Markdown 是一种纯文本标记语言，用少量符号（#、*、-、[]() 等）表达文档结构。源文件本身就是可读的纯文本，经解析器渲染后成为 HTML、PDF 或其他格式。它的设计哲学可以概括为一句话：让源文件在不渲染时也读得懂。

1.2 起源

  • 2004 年，约翰·格鲁伯（John Gruber） 创建了 Markdown，亚伦·斯沃茨（Aaron Swartz） 参与语法设计并做测试。
  • 约翰·格鲁伯同时写了一个 Perl 脚本 Markdown.pl，把 Markdown 文本转成合法的 XHTML/HTML。这个脚本最后一次更新停留在 2004 年 12 月 17 日。
  • 它的设计灵感主要来自纯文本电子邮件的排版格式，目标是让作者用易读、易写的纯文本编写文档，并能方便地转换为 HTML 等格式。在它之前已有 setext、Textile、reStructuredText 等同类语言。

1.3 发展历程：从”一个脚本”到”多种方言”

由于 2004 年的原始规范文字较为简略、存在歧义，不同软件的解析实现逐渐出现分化。此后 Markdown 的标准化与扩展大致经历了以下三个阶段：

  1. 变体丛生（2004 起）：Markdown Extra、MultiMarkdown、kramdown、Pandoc 的 Markdown 等，各自增加表格、脚注、定义列表等功能，互不兼容。
  2. CommonMark（2014 起）：John MacFarlane、Jeff Atwood 等人制定了一份无歧义的规范 + 配套测试套件，专门消除上述分歧。今天多数主流工具（GitHub、GitLab、Discourse、Stack Overflow 等）都以内核兼容 CommonMark 为基础。
  3. GFM（GitHub Flavored Markdown）：GitHub 在 CommonMark 之上加了一层自己的扩展，规范为 GFM，补充了表格、任务列表、删除线、自动链接、脚注、提示块（Alerts）等。它是目前写 README、Issue、技术文档时最常被说到的”事实标准”。

如今 Markdown 广泛用于博客与文档站点、代码仓库 README、在线论坛、协作笔记、学术写作以及大模型交互等场景，文件扩展名通常为 .md 或 .markdown。

1.4 主要特点

  • 纯文本书写：使用普通文本编辑器即可编写，不依赖专有排版软件，文件可长期保存、便于版本管理。
  • 可读性强：源码本身接近自然语言，符号简洁，未渲染时也容易读懂。
  • 跨平台、可移植：同一份 .md 文件可在 Windows、macOS、Linux 及各类在线平台之间流转。
  • 易于转换：可方便地转换为 HTML、PDF、Word、幻灯片等格式。
  • 语法轻量：核心语法只需少量符号即可完成标题、列表、引用、代码等常见排版。
  • 可扩展：在核心语法之上，各平台通过扩展语法支持表格、任务列表、数学公式、内部链接等高级功能。

二、标准 Markdown 语法

2.1 标题（Headings）

使用井号 # 表示标题，# 与标题文字之间需保留一个空格，共支持一至六级。

此外，原始 Markdown 还支持下划线式（Setext）标题写法，仅对应一、二级：

要点：

  • 一篇文档建议只用一个 # 作为主标题，其余按层级递进，不要跳级（如 ## 直接到 ####）。
  • 标题行末尾的 # 会被忽略：## 标题 ## 等价于 ## 标题。
  • 标题会自动生成锚点，供目录跳转使用。

2.2 段落与换行（Paragraphs & Line Breaks）

  • 分段：用一个或多个空行隔开，空行两侧就是两个段落。
  • 段内换行（硬换行）：在一行末尾加两个或更多空格再回车；或行尾加一个反斜杠 \再回车。
  • 仅按一次回车，行尾没有两个空格或一个反斜杠 \，在多数渲染器中只是“软换行”，会被合并成同一段。
  • 很多编辑器会自动删除行尾空格，导致硬换行失效，因此跨平台文档建议使用 \。

2.3 强调（Emphasis）

效果 语法 说明
斜体 *文字* 或 _文字_ 常用 *
粗体 **文字** 或 __文字__ 常用 **
粗斜体 ***文字*** 三层星号
删除线 ~~文字~~ GFM 扩展

要点：

  • 强调符号必须紧贴文字内侧：** 粗体 ** 中的空格会让它失效。
  • 下划线式在英文单词内部不生效：snake_case_name 不会被解析为斜体。星号式更安全，推荐统一用 *。
  • 中文排版中没有“斜体”传统字形，斜体在部分字体下会被渲染为伪斜体（倾斜变形），视觉效果一般。中文强调优先用粗体。

要点：

  • 列表标记后必须有空格，-项目 不是列表。
  • 列表前留空行，否则可能被并入上一段。
  • 有序列表的起始数字决定编号，后续数字会被自动重排（写 1. 1. 1. 也能得到 1/2/3）。
  • 列表项之间留空行会变成”松散列表”（每项各成一段），不空行则是”紧凑列表”。
  • 列表项里要放多段文字或代码块时，需按缩进对齐。

  • 把图片当链接：[![alt](img.png)](https://example.com)。

2.7 引用块（Blockquotes）

在段落每行开头添加 > 表示引用；引用可以嵌套，也可以包含列表、代码块等其他元素。

2.8 代码（Code）

行内代码：用反引号包裹行内代码，适合标注变量名、命令或短片段。代码里若本身含反引号，外层用两个反引号并加空格。

围栏代码块：用至少三个反引号或三个波浪号包裹，开头标记语言名可做语法高亮。

缩进代码块：原始 Markdown 中，缩进四个空格（或一个制表符）的行会被解析为代码块。无语言标注、无高亮，现已不推荐。

要点：

  • 围栏代码块可读性更好、支持高亮，优先使用；波浪号 ~~~ 适合代码里含反引号的场景。
  • 代码块内的 *、_、[] 等符号一律按字面显示，不会被解析为格式。这是展示 Markdown 语法本身的标准做法。
  • 语言标识写在围栏后，名称需与渲染器支持的高亮库一致（python、js、bash、json、yaml、sql、diff 等）。

2.9 分隔线（Horizontal Rules / Thematic Breaks）

单独一行写三个或更多的 -、* 或 _（中间可有空格）。

注意：上一行若紧邻文字，--- 可能被解析为”标题下划线”（Setext 语法），分隔线前后各留一个空行最稳妥。

2.10 表格（Tables）

归类提醒：表格不是原始 Markdown / CommonMark 的标准语法，而是 GFM 扩展。但 GitHub、GitLab、Obsidian、Typora、绝大多数静态站点都支持，已成为事实标准，故在此讲解。

  • 第一行为表头，第二行为分隔行，使用 - 划分列、| 分隔单元格。
  • 分隔行中的冒号 : 控制对齐方式：左对齐 :---或---、右对齐 ---:、居中对齐 :---:。

渲染效果：

姓名 年龄 城市
张三 28 武汉
李四 32 北京
王五 25 上海

要点：

  • 每个单元格里若要写竖线 |，用 \| 转义。
  • 单元格内可用行内格式（**粗体**、`代码`、链接）。
  • 首尾的 | 可省略，但保留更易读。
  • 表格不能合并单元格，也不能在单元格内换行。需要时改用 HTML <table>。
  • 列宽由内容决定，源文件中不需要对齐竖线（对齐只是便于阅读源码）。
  • 表头不可省略：没有分隔行就不构成表格。

2.11 转义字符与内嵌 HTML

转义字符

部分符号在 Markdown 中有特殊含义，在符号前加反斜杠 \ 可将其转义为普通字符。

可转义的字符包括 \ ` * _ { } [ ] ( ) # + - . ! < > | ~ 等。

内嵌 HTML

标准 Markdown 允许直接写入部分 HTML 标签，例如换行、加粗、换行线、图片等；复杂排版可借助 HTML 实现，但跨平台兼容性需自行测试。

一句话总结

标准 Markdown（CommonMark）保证”到哪都能渲染”，扩展语法（GFM、Obsidian 等）带来更丰富的表达。先掌握标准，再按需引入扩展，并始终留意兼容性——这是用好 Markdown 的关键。
